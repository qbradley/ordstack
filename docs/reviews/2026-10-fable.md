# Adversarial review of `ordstack` (commit 97c2ab8, branch impl-0.1)

**Verdict: no soundness hole found.** Every program I wrote that would have produced undefined behaviour was rejected by the borrow checker; every program that compiled ran clean under Miri (Stacked Borrows and Tree Borrows) and natively with the debug shadow enabled. The findings section is therefore empty. The documentation section lists three statements the code does not support (none affects safety). The attack log follows.

Method: read `SOUNDNESS.md`, then every file in `crates/ordstack/src/` (3052 lines), then the compile-fail tests. Wrote a scratch crate with 16 "expected compile-fail" programs and 6 Miri programs on the train box, depending on the unmodified checkout by path. Toolchain: stable for compile tests, nightly Miri for runtime. Scratch directory removed afterwards; the repository was not modified on either machine.

## 2. Documentation claims the code does not support

**D1. `lib.rs` "Failure" section: "A failed allocation changes no object: lengths, capacities, pointers and frame ends are as before, and no value is lost."**
False for `Frame::try_alloc`. `frame.rs:188-197`: `try_alloc(value)` calls `try_alloc_array::<T>(1)?` and on `Err` returns with `value` still owned by the function, so it is dropped. The method's own doc ("or drops it and reports why not") and SOUNDNESS.md ("dropped by `Frame::try_alloc` and by the panicking methods") are correct; the crate-level statement is not. Not a safety issue.

**D2. `SOUNDNESS.md` "Why I holds": "Every handle type mentions its brand in a covariant position, so a brand can only be shortened".**
`SVec<'v,'f,T>` and `SString<'v,'f>` are invariant in `'f` (they hold `&'v mut Frame<'f>`); H4 of the same document says so. The sentence is wrong for those two types. The error is in the safe direction (invariance is stricter than covariance), so the argument survives, but the sentence should say "covariant or invariant".

**D3. `SString::with_capacity_in` / `from_str_in` doc: "# Panics: If the stack is exhausted."**
`with_capacity_in(usize::MAX, ..)` panics with `CapacityOverflow` (from `Stack::try_bump`'s `checked_add`), not `Exhausted`. The `SVec` equivalent documents this; the `SString` wrappers omit it. Cosmetic.

Everything else I checked holds: 70 public functions and 62 `unsafe {` blocks (counts match SOUNDNESS.md); 14 ui fail cases with 14 pass twins; `scripts/check.sh` runs Miri under both aliasing models, ASan with build-std, and the fuzz target as README states; `tests/panics.rs` covers the destructor, clone, retain, alloc_with and extend rows of H3 as H3 claims; the H6 claim that an over-aligned zero-size type succeeds is true; the H3 `freeze_into` row (exhausted destination drops the source vector with its elements) is true (observed 100 drops).

## 3. Attacks tried and what stopped each

### A. Lifetimes and variance

| Attack | Program (abbreviated) | Result |
|---|---|---|
| Lengthen a sub-frame to its parent's brand | `fn pin<'a>(f:&mut Frame<'a>)->SBox<'a,u32>{ let mut g:Frame<'a>=f.sub(); g.alloc(1) }` | E0621: `sub` returns `Frame<'_>` tied to the `&mut` borrow, not `'a`; annotating it as `'a` demands `&'a mut f`. In `main` the same annotation compiles but leaves `f` borrowed for its whole brand (sound: `g` becomes the only usable frame). |
| Escape a sub-frame through a function | `fn escape<'a>(f:&mut Frame<'a>)->Frame<'a>{ f.sub() }` | E0621. |
| Escape an `above` frame with the frame brand | `fn escape<'v,'f>(v:&mut SVec<'v,'f,u32>)->Frame<'f>{ v.above() }` | "lifetime may not live long enough": the result is bounded by the `&mut` borrow. |
| Return a frozen slice bound to the `&mut Stack` borrow, then `st.reset()` | `fn make<'a>(st:&'a mut Stack)->SSlice<'a,u32>` then `st.reset()` while the slice lives | E0499. |
| Drop-order: handle declared before the stack | `let b:SBox<u32>; let mut st=..; b=f.alloc(1);` and the `ManuallyDrop<SBox>` variant across a block | E0597 `st does not live long enough` in both (the `ManuallyDrop` version fails on the later *use*, through NLL liveness, not on drop). |
| `'static` stack via `Box::leak` | `SBox<'static,u32>`, `SSlice<'static,u8>`, `SBox::leak` → `&'static mut`, pushed into an `SVec` on a second stack | Compiles and is correct; Miri (SB, TB, `-Zmiri-ignore-leaks`) clean. The stack is never dropped, so nothing dangles. |

### B. `mem::swap` / `mem::replace` / `ManuallyDrop` / `Option::take`

| Attack | Result |
|---|---|
| `mem::swap` a sub-frame of stack A with the root frame of stack B, allocate from both, then use A's parent while the swapped-out sub-frame is still alive | E0499 on the parent: the swap unifies the two brands to their intersection, so the parent stays borrowed as long as *either* variable is used. Confirms H5. |
| Same swap chain but used legally (three stacks, swap `v.split_above()`'s frame with a third stack's frame, allocate and grow an `SVec` on the swapped-in frame, write through the `split_above` slice, swap back, grow `v`, freeze, `mem::replace` a frame with `Frame::sub`) | Compiles; Miri SB/TB and native all `ok`. Each frame carries its own `&Stack` and `end`, so swapped values stay consistent. |
| Swap unifying brands then using the earlier-allocated handle | The compiler *extended* the borrow of `v` to cover a handle allocated before the swap (E0597) — more conservative than needed, never less. |
| `ManuallyDrop<SVec<Option<SBox<'x>>>>`, store a block from the `split_above` frame into the vector's own element, then `ManuallyDrop::into_inner(v).freeze()` / `v.len()` / `v.push` | E0505 / E0502 / E0499: any use of `v` makes `'x` live again (NLL liveness), which conflicts with the `split_above` loan. H1's "the vector can then never be used again" holds. |
| Same, storing the **`Frame`** itself (`SVec<Option<Frame<'_>>>`, `elems[0]=Some(up)`) then `v.push(None)` | E0499. |
| Lower frozen `ManuallyDrop<SBox<Cell<Option<SBox<'x>>>>>` allocated before the vector; store `up.alloc(..)` into the cell through `above()`, then `v.push` and `cell.take()` | E0499 on `v.push`: the cell's type mentions `'x`, and the cell is used after, so `'x` stays live and `v` stays borrowed. |
| `SBox<'g, SVec>` on another stack, `SBox::leak`, then grow, `above`, push after the destination frame allocates | Compiles (sound); Miri clean. Trying `leaked.freeze_into(&mut fb)` is E0507 (cannot move out of `&mut`). |
| `SFixedVec<SVec<u32>>` in a frozen block of the same frame holding an `SVec` on that frame; push, `split_above`, grow; then `f.reset_above()` while the fixed vec lives | Legal uses: Miri clean. `f.reset_above()`: E0499 (`f` is borrowed by the vector inside `fv`, and `fv`'s drop keeps the borrow alive). |
| `mem::replace` through `DerefMut` on `SBox`, `mem::swap` of two `SSlice`s, `Option::take` on handles | Only move or in-place replace values; no stack state involved. Not written as separate programs; reasoned from the code (no handle exposes its frame or pointer). |

### C. Drop check

| Attack | Result |
|---|---|
| Push a block branded by a *sub-frame* of `fb` into a vector on stack A, then `v.freeze_into(&mut fb)` (would place the copy over the sub-frame's block) | E0499: `fb` is still borrowed by the sub-frame because `v`'s element type mentions its brand. |
| Elements with destructors that read lower frozen blocks (`D` with a thread-local counter), dropped through `SVec::drop`, `SSlice::drop`, `IntoIter::drop`, `truncate`, `retain` | All memory read is below the frame's end and still mapped; Miri clean. |

### D. Panics at the H3 call-outs (all under `catch_unwind`, then the frame/vector reused, then `freeze`/allocate again; Miri SB + TB + native)

Predicate panic in `retain` (gap closed, length restored, contents verified); destructor panic of a rejected element in `retain`; destructor panic in `truncate`; `Clone` panic in `alloc_slice_clone` then allocate again; iterator panic in `extend` (prefix kept) and in `from_iter_in` (vector dropped); `alloc_with` closure panic; `SString::truncate` off a char boundary (string unchanged); `freeze_into` to an exhausted destination (source dropped with all 100 elements); destructor panic while dropping a frozen slice, then frame reused. Observed drop count 118, deterministic across the three runs; no Miri report.

### E. Zero-size and over-aligned types, capacity arithmetic

`#[repr(align(8192))]` ZST through `alloc`, `alloc_slice_copy`, `SVec` (push, `extend_from_slice`, `freeze`), `SBox::leak`: succeeds with a dangling pointer, `end_offset` stays 0. `#[repr(align(8192))]` non-ZST: `alloc` panics `AlignTooLarge`, `SVec::try_push` returns `Err` with length 0. `SVec<Z>` of a ZST with `Drop`: 1000 pushes, `truncate`, `retain`, `insert`, `remove`, `swap_remove`, `split_above` plus an allocation above, `shrink_to_fit`, `freeze`, `into_iter`: every value dropped exactly once (1012 total with the fixed vec). `SFixedVec<Z>` with `try_push` at capacity, `pop`, `into_slice`. `Stack::with_reserve(0)`: capacity 0, ZST `alloc` succeeds, `try_alloc(1u8)` and `SVec<u8>::try_push` fail, empty `alloc_slice_copy` succeeds, `trim_above`, `reset_above`, `trim`, `reset` all no-ops; Miri clean (the `without_provenance` base is never dereferenced). `try_reserve(capacity)` fails `Exhausted` with the vector unchanged; `try_reserve(usize::MAX)` fails `CapacityOverflow`; `shrink_to_fit` with `len>0` and with `len==0` (buffer given up, capacity 0) then regrow; `freeze` of an allocated empty vector; `trim_above` / `trim` followed by fresh allocation on the discarded pages (contents re-written before read). Verified by reading that every size product is `checked_mul`/`checked_add` and that the plain multiplications (`end_off`, `freeze`, `shrink_to_fit`, `check`) are bounded by an existing buffer.

### F. Claims asserted without a stated reason (checked by reading)

- "`top >=` the end of every live object" (T): every `reset_to` caller holds `&mut` (or ownership) of the object whose end it resets to, and the chain property (only one usable frame per stack, every other one borrowed) holds because the only constructors are `Stack::frame(&mut)`, `Frame::sub(&mut)`, `SVec::above/split_above(&mut)`; `mem::swap` relocates frame values but cannot create a second usable frame on a stack (tested above).
- `try_extend`'s `assert_eq!(old_end, top)` is unreachable from safe code: follows from T plus the reset on the line before.
- `Stack::offset_of` is only called when `allocated()` is true (`start_off`, `freeze`, `shrink_to_fit` are all guarded).
- `alloc_slice_copy`'s "`src` is disjoint from the fresh block": every `&[T]` into region memory is either below the frame's end (`Deref` of a handle, `split_above` slice) or branded by a borrow of the frame (`leak`), so a `src` above `end` would make the call ill-typed.
- Debug shadow (`REGIONS` thread-local): `try_with` guards every access, no user code runs while the `RefCell` is borrowed, so no re-entrant borrow panic; stale entries after `mem::forget(stack)` are harmless because the mapping is never unmapped.
- Threads: `Stack` has `Cell` + `NonNull`, every handle has `NonNull` or `&Stack`; no `unsafe impl`. `AllocError` is `Send` but holds no pointer.

What I did not do: run the crate's own test suite, fuzzer or ASan (the brief asks for independent programs); exercise macOS `MADV_FREE`; or attempt a mechanised proof. The one residual I would still watch is `Stack::offset_of` and `release_above` being `debug_assert!`-only internal contracts (H10) — correct today because every caller is guarded, but a future caller could silently break them in release builds.
