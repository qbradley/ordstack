**Incorrect proof statement: H3 excludes reentrant allocation too broadly.**

[SOUNDNESS.md:236](SOUNDNESS.md:236) says:

> So the user code cannot name the object in its intermediate state, nor allocate from its frame.

A frozen handle does not borrow its allocating frame. Its element’s destructor can therefore allocate through that very frame:

```rust
use ordstack::{Frame, Stack};
use std::cell::RefCell;

struct Reenter<'a, 'f>(&'a RefCell<Frame<'f>>);

impl Drop for Reenter<'_, '_> {
    fn drop(&mut self) {
        let value = self.0.borrow_mut().alloc(42u64);
        assert_eq!(*value, 42);
    }
}

fn main() {
    let mut stack = Stack::with_reserve(4096);
    let frame = RefCell::new(stack.frame());

    let value = frame.borrow_mut().alloc(Reenter(&frame));
    drop(value); // Its destructor allocates through its allocating frame.
}
```

This program passed borrow checking. **It is not a UB reproducer.** The allocation is safe because `frame.end` already covers the object being destroyed. Reentrant allocation starts beyond that boundary. The same distinction matters for frozen slices, fixed vectors, and owning iterators.

H3 should separately establish:

- Growable containers retain an exclusive frame borrow.
- Frozen handles permit reentrant frame access, but their storage remains below the frame’s protected end.
- Shared comparison, hashing, and formatting calls can permit shared reentrancy and interior mutation; they expose no inconsistent allocation state.

**Separate documentation discrepancies**

- [lib.rs:111](crates/ordstack/src/lib.rs:111): “A failed allocation changes no object … and no value is lost” is too broad. `Frame::try_alloc` drops its input on failure, potentially executing arbitrary caller code. The method’s own documentation correctly says this.
- [error.rs:11](crates/ordstack/src/error.rs:11): requests exceeding `isize::MAX` do not necessarily report `CapacityOverflow`. A representable byte count larger than the region can report `Exhausted`.
- [vec.rs:49](crates/ordstack/src/vec.rs:49): “room for exactly `cap` elements” needs a ZST exception: those vectors report `usize::MAX`.
- `Frame`’s type documentation says reclamation occurs when the lower object is next “used.” Read-only queries and vector operations within existing capacity need not reclaim anything. The crate-level lazy-reclamation explanation is more precise.

This complete program demonstrates the first three discrepancies:

```rust
use ordstack::{AllocErrorKind, SVec, Stack};
use std::cell::Cell;

struct CountDrop<'a>(&'a Cell<usize>);

impl Drop for CountDrop<'_> {
    fn drop(&mut self) {
        self.0.set(self.0.get() + 1);
    }
}

fn main() {
    let drops = Cell::new(0);
    let mut stack = Stack::with_reserve(0);
    let mut frame = stack.frame();

    assert!(frame.try_alloc(CountDrop(&drops)).is_err());
    assert_eq!(drops.get(), 1);

    {
        let mut values = SVec::<u8>::new_in(&mut frame);
        let error = values
            .try_reserve(isize::MAX as usize + 1)
            .unwrap_err();
        assert_eq!(error.kind(), AllocErrorKind::Exhausted);
    }

    let values = SVec::<()>::with_capacity_in(3, &mut frame);
    assert_eq!(values.capacity(), usize::MAX);
}
```
